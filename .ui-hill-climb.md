# LearnHarness UI hill-climb context

Project guidance, not authorization to start a run. Select the target and iteration/model settings for each run; the targets below are alternatives, not a request to optimize all of them at once.

## Outcome

Improve the complete conversation-led learning workflow: reading, answering, practising, navigating and resuming work. A pleasant individual screenshot is not sufficient if the sequence of work becomes harder.

## Targets

### iPhone

Optimize for a small-screen iPhone. Derive the relevant touch, keyboard, orientation, scrolling and enlarged-text checks from the app's workflows. Browser emulation supports iteration; actual-iPhone observations are a separate evidence source. Include non-target compatibility observations under functional continuity without making other devices optimization targets.

### iPad

Available target. The owner's pen-writing capability is recorded under [explicit requirements](#explicit-requirements). This does not select iPad as the current run's optimization target.

### Laptop

Available target. No additional laptop-specific layout or input constraints have been agreed; the target name is enough to begin discovery.

## Additional scoring criteria

### Learning-content usability

Can the learner read and use problems, maths, tables, figures, handwriting and answer fields while keeping the relevant question, their work and necessary controls accessible?

Assess presentation and tool use, not the effectiveness of a teaching policy. Use the shared grading anchors and threshold from the skill.

## Reference qualities

- **T3 Code mobile:** owner-selected inspiration for a coherent mobile experience and navigation.
- **Craft:** owner-endorsed inspiration for pleasant reading and easy navigation.
- **Official OpenCode iOS beta:** owner-selected interest, but imagery has not been verified. Treat it as uninspected unless first-party evidence is obtained before the review pack is frozen.

Learn from qualities rather than cloning another app's workflow. Keep owner-supplied screenshots and their text local; still images do not establish interaction smoothness.

## Review considerations

Under functional continuity, inspect learning capabilities, saved and unfinished work, input/submission, dictation and settings. A workflow means what the learner can accomplish, not today's sequence of screens or actions. Under reading and learning-content usability, inspect selection, zoom and access to the learner's question and work. Tests and workflow checks inform the reviewers' scores and promotion verdicts; existing controls and contracts are not automatically UI constraints.

## Explicit requirements

Apply owner-approved product requirements from the fork vision with their source; distinguish those requirements from current implementation choices. Use disposable data and keep credentials and private learner data out of experiment evidence.

- **iPad pen writing:** the learner must be able to use a pen/stylus to write on a canvas-like surface. The current canvas implementation, editor and access path are replaceable; judge the resulting writing experience. Source: owner clarification, 2026-11-05.

## Design freedom and preferences

The entire app is available for redesign in a whole-app run. Implementers choose layouts, navigation, controls, typography, palettes, motion and gestures; reviewers decide whether the complete experience improves. References express desired qualities. Steer preferences through the scoring criteria rather than preserving today's UI by default.

## Project decisions

Read [the fork vision](docs/fork-vision.md) for owner-approved product direction, not a prescription for the existing UI. Follow repository instructions when inspecting or changing the application.
